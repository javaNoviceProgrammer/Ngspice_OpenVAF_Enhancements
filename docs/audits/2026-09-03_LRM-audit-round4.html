Conformance audit · Accellera VAMS-2023 · fourth pass, fifteen areas

The fourth LRM audit: the standard's own examples, run one clause at a time

An independent pass over openvaf-r and the ngspice-46 OSDI layer against the Verilog-AMS 2023 LRM, over the same fifteen areas the first two audits used. Three earlier passes had already fixed 53 divergences, so this one changed instrument: wherever the LRM prints a worked example, that example was compiled and run verbatim, and wherever it states a numeric rule, the number was measured rather than the construct merely compiled. Fourteen findings, every one reproduced on both binary pairs and traced to a named line. Four were silent: a discipline's tolerance override that never reaches the solver, two noise sources that disappear or triple on a switch branch, and a string that loses its tail. (A fifteenth, a transient starting from the wrong voltage, was published and is withdrawn; the two switch-branch faults and the tolerance override have since been fixed, leaving one silent divergence open.) Three of the LRM's own printed examples do not compile.

1The verdict

The numerical core holds again. What gave way this time is the layer where the language lets one declaration modify another: a discipline overriding a nature, a later contribution reclassifying an earlier one, a netlist multiplier reaching a source the compiler has already scaled.

The prior three audits established that contributions, derivatives, filters, noise and parameter resolution are right, then that state spanning calls and iterations is right. This round's fifteen areas were the same list the first audit used, but the method was different: every worked example printed in the audited clauses was compiled as written, and every rule that yields a number was measured. Three of the LRM's own examples fail. 32 'h 12ab_f001 (2.6.1, Example 5) is lexed as a real number. The sample-and-hold in 5.10.3.1, with its null arguments cross(V(smpl) - thresh, dir, , , en), is a type error. The ttl discipline of 3.6.2.5, whose whole point is flow.abstol = 10u, compiles and then behaves as if the line were absent.

The sharpest result is the last one. A discipline may override the tolerance of the nature it binds (3.6.2.5), and a nature may be derived from a discipline's flow so that it inherits that override (3.6.2.6, whose example says in a comment “abstol = 10u as modified in ttl”). The override parses, produces no diagnostic, and has no effect anywhere: a.flow.abstol reads 1e-6, the derived nature reads 1e-6, the compiled .osdi tables carry no override, and the per-node tolerance that Enhancement-539 added to the simulator walks a parent chain that stops exactly where a discipline-derived nature begins. A model author who tightened a tolerance by the LRM's own mechanism is being solved with the loose one, silently. Fixed after the audit, in all four places at once — §3 records how, and the LRM's own two examples now read 1e-05 on both routes.

The second group is noise on a switch branch, the construct 5.6.5 defines for relays and ideal switches. Two different things go wrong on it, and neither goes wrong on a plain branch. A potential contribution that is only a noise source, written in the arm after a flow contribution, is dropped: the output shows nothing but the load resistor's thermal noise. That is a direct consequence of the rule Enhancement-531 introduced to keep BSIM4's access-region noise from reclassifying a collapse branch: a noise-only right-hand side no longer sets the branch's source kind, which was right for that model and is wrong for a noise-only potential source, because 5.6.1.3 says a potential contribution discards any retained flow. And a flow-arm noise source, when the multiplier comes from the netlist's m= rather than from Verilog-A's #(.$mfactor()), scales as m1.5: nine parallel devices report twenty-seven times the noise current of one, where 6.3.6 says three. Both were fixed after the audit, and one line explains both: a switch branch carries its branch current as an unknown, so everything either arm contributes — classification and sources alike — goes through that one equation, and both defects were code that had only ever had to be right about a plain branch. §3 records each fix.

Reading the fifteen together, one pattern explains most of them: a construct is implemented on the path it was first needed for and not on its siblings. Null arguments were implemented for the Laplace filters (E-453) and not for the event functions the same grammar rule covers. Attribute access was implemented for natures (E-45) and not for the discipline that overrides them. Initial conditions reach netlist nodes and not the internal nodes an OSDI device declares. The multiplicity scaling of noise is right on the route the LRM examples use and wrong on the route every SPICE deck uses.

2How this pass ran

The fifteen areas are the ones named in the brief, which are the first audit's areas. To avoid re-measuring what three passes had already pinned, each area started from the LRM text rather than from the compiler: the relevant clauses were read in full (2, 3, 4.2 to 4.7, 5, 6.2 to 6.5, 9.4 to 9.18, 10, Annexes C and D), and every printed example and every stated number became a test. Where an earlier audit's coverage map already claimed a rule, the rule was re-measured only if the new test was a different shape.

Two instruments carried most of the weight. The first was verbatim compilation of the LRM's examples: the based-literal table of 2.6.1, the string-operator examples of 3.3, the four analog-function examples of 4.7.1 and 4.7.3, the sample-and-hold of 5.10.3.1, the ttl disciplines of 3.6.2.5 and 3.6.2.6, the value-retention module of 5.6.1.3, the implicit diode of 5.6.6, the CCCS of 5.6.1.3, badres and parares of 6.3.6, the bit-error-rate module of 5.10.2. Three of these do not compile, one compiles and gives the wrong answer, and the rest give the LRM's answer.

The second was paired measurement by route. Where the LRM gives one rule and the implementation has two ways in, both were driven with the same module: the netlist m= beside the Verilog-A #(.$mfactor(9)); a potential arm written first beside the same arm written second; the same event function with an explicit zero beside a null argument. Every headline number below is one half of such a pair, and the other half is the control that makes it a finding rather than an opinion. One entry did not get that treatment and did not survive it: the .ic claim of §7 paired a netlist node against an OSDI internal node when the pair it needed was an OSDI internal node against a built-in device's internal node — which behaves identically. It is withdrawn.

Each finding was then pushed until it named a cause in openvaf/lexer, openvaf/parser, openvaf/hir_def, openvaf/hir_ty, openvaf/hir_lower, openvaf/sim_back, openvaf/osdi or ngspice-46/src/osdi, and each was re-run on the second binary pair. Candidates that turned out to be documented, deliberate, or correct on a closer reading are kept in §7 so that a fifth pass does not spend its budget on them.

bug · silent · FIXEDA discipline's nature-attribute override parses and is then dropped everywhere: attribute access, the OSDI tables, derived natures, and the per-node solver toleranceLRM 3.6.2.5 / 3.6.2.6 / 3.6.1.2
3.6.2.5 lets a discipline override the attributes of the nature it binds (“the keyword flow or potential, then the hierarchical separator . and the attribute name”), and 3.6.2.6 lets a nature be derived from ttl.flow so that “if the nature bound to the potential or the flow of a discipline changes, the new nature shall automatically inherit the attributes for the changed nature”. The LRM's two examples were compiled together, unchanged apart from the access names, and the overridden tolerance is read back through 5.5.3's attribute access:
nature ttl_curr; units = "A"; access = Itl; abstol = 1u; endnature discipline ttl; potential ttl_volt; flow ttl_curr; flow.abstol = 10u; enddiscipline nature ttl_net_curr : ttl.flow; endnature // LRM comment: "abstol = 10u as modified in ttl" discipline ttl3; potential ttl_net_volt; flow ttl_net_curr; enddiscipline ttl a; ttl3 c; a.flow.abstol = 1e-06 LRM: 1e-05 (the discipline's override) c.flow.abstol = 1e-06 LRM: 1e-05 (inherited through ttl.flow) a.potential.abstol = 1e-04 (correct: no override on the potential side)
Nothing is said on any channel. The neighbouring mechanisms all work, which is what makes this a drop rather than an unimplemented feature: a nature-level override in a derived nature (abstol = 1m) is honoured, a user-defined attribute (maxval = 12.3) is readable, and the `VOLTAGE_ABSTOL define of Annex D reaches p.potential.abstol exactly.
Cause, in four places. hir_def/src/item_tree/lower.rs:664-712 lowers each discipline item; for a qualified name such as flow.abstol the kind is recorded as FlowOverwrite, but the only line that evaluates an attribute's value (“All other attributes - evaluate ast expression”) sits inside the kw::domain arm of the match, so the override is stored with value: None. osdi/src/ndatable.rs:52-67 (OsdiAttribute::new) returns None for a value-less attribute, so the override never enters the .osdi discipline tables. hir_def/src/nameres.rs:441-466 resolves net.flow.attr straight to the bound nature's attribute (the DisciplineAttrId scope item is commented out), so attribute access cannot see an override even if one were stored. And ngspice-46/src/osdi/osdicallbacks.c:280-344 (osdi_node_abstol, Enhancement-539) resolves a node's tolerance by walking the nature's parent chain and breaks out as soon as parent_type != NATREF_NATURE, so a nature derived from ttl.flow returns 0.0 and the circuit-wide default is used. The compliance tracker (§3.3) claims deriving from a discipline's nature “with full attribute inheritance”; the inheritance is full only when the discipline has nothing to add.
repro: discovr.va / discovr.cir
Resolved (2026-09-03, after the audit), in the four places this entry names. The first was the root: the line that evaluates an attribute's value moved out of the kw::domain arm to the outer one, so an override is no longer stored with value: None — which is also all the .osdi tables needed, since collect_discipline_attrs already had a flow/potential slot per discipline and was only ever skipping value-less attributes. The DisciplineAttrId scope item that was sketched and commented out is now real: its body was already lowered exactly like a nature attribute's, so it types (discipline_attr_ty) and lowers (Ref::DisciplineAttr) the same way, and net.flow.<attr> / br.flow.<attr> consult the discipline's override before the nature. The nature-chain walk gained the 3.6.2.6 link: where a nature's parent is written ttl.flow, the discipline's override of that side is read at the hop rather than stepped past. And in the simulator, osdi_node_abstol now reads a discipline's own attribute range (the table lays them out [flow][potential][user] from attr_start) both for a node's own binding and for a parent link that is a discipline, instead of breaking out of the loop.
after the fix, the same two LRM examples: a.flow.abstol 1.00e-05 LRM 1e-05 (the discipline's override) c.flow.abstol 1.00e-05 LRM 1e-05 (inherited through ttl.flow) a.potential.abstol 1.00e-04 (unchanged: nothing overrides it) .osdi discipline table: flow.abstol = 1e-05 in ttl's flow range per-node solver tolerance, a discipline overriding potential.abstol = 1n: OSDI: node 1 convergence abstol = 1e-09 (was 1e-06, the nature's own) OSDI: node 2 convergence abstol = 1e-09 (derived route: was nothing at all)
The illegal overrides stay illegal: 3.6.1.2 forbids changing units or access, the warning added for the §5 finding says such a declaration “has no effect”, and both the lookup and the .osdi export now skip them so that promise holds — u.flow.units still reads "A" under flow.units = "mA". Pinned by nine new checks over a new lrmdisc_ovr.va in examples/lrmdisc_examples/ (34 checks, both solvers), including the two table checks, for which the suite's dump_nda.c harness now dumps disciplines as well as natures.
bug · silent · FIXEDA noise-only potential contribution in the later arm of a switch branch is droppedLRM 5.6.1.3 / 5.6.5 / 4.6.4
5.6.1.3: “contributing a potential to a branch which already has a value retained for the flow results in the flow being discarded and the branch being converted into a potential source”. No exception is made for a contribution whose value happens to be a noise function. Two modules differ only in which arm comes first:
// potential arm first // flow arm first if (sw) V(p,n) <+ white_noise(1e-12,"wn"); if (sw) I(p,n) <+ white_noise(1e-12,"wn") + V(p,n)*1e-3; else I(p,n) <+ white_noise(1e-12,"wn") + V(p,n)*1e-3; else V(p,n) <+ white_noise(1e-12,"wn"); onoise at node 2, potential arm active (sw=1 left, sw=0 right), 1 kΩ from an AC-grounded source: left 1.000e-06 V/√Hz LRM 1e-6 right 4.071e-09 V/√Hz = √(4kT·1kΩ): the load resistor alone; the device's source is gone
Adding any deterministic term restores it: V(p,n) <+ 0.1 + white_noise(...) in the same second arm gives 1e-6. A runtime switch (if (V(c) > 0.5)) behaves the same as the parameter one. The flow arm's own noise is not affected.
Cause. hir_lower/src/stmt.rs:921-941 (contribute_value_, from Enhancement-531): a contribution whose right-hand side is noise-only does not define the branch's IsVoltageSrc place if the place already exists. That rule was written so BSIM4's unconditional I(di,d) <+ white_noise(...) would stop reclassifying a collapse branch, and E-531 states the reasoning: “a noise-only contribution carries no source kind and must not reclassify anything”. For a potential source the reasoning inverts: 4.6.4 makes the noise zero in large-signal analyses, so the arm contributes V = 0 plus a noise source, and 5.6.1.3 makes that a potential source. With the flow arm lowered first the place exists and stays false, the branch remains a flow source, and sim_back/src/dae/builder.rs:576-582 then sees a trivial voltage source with no current unknown and builds no source equation for it, noise included. Recorded with E-531 as the prior art it is: the rule is correct for its motivating case and one case too wide.
repro: swnoise2.va / swnoise2.cir (4.07e-9) · control: swnoise.va with sw=1 (1e-6)
Resolved (2026-09-03, after the audit). E-531's rule was asking a question the SSA place table cannot answer. get_place is monotonic — it finds an IsVoltageSrc place created anywhere in the function — so a classification made in one arm of an if made its own sibling look already classified. That is exactly why the fault was an order dependence and not a missing feature: written the other way round, the same two arms worked. The lowering now tracks which branches have been classified on the path that reaches this contribution (hir_lower/src/ctx.rs: a set saved and restored around each make_cond arm, then merged at the join), and a noise-only right-hand side declines to reclassify only when a classification genuinely reaches it. E-531's motivating case is untouched, because there the earlier contribution is on the same path: BSIM4 still builds, and the collapse branch still collapses — its arm gives 0.000e+00 noise and holds the short at v = 0. Both arm orders now read 1e-6, and the potential arm still divides by √m (3.333e-07 at m=9). Pinned by five new checks in examples/lrmnoise_examples/ (nsw.va, 25 checks, both solvers), which assert the switch branch value for value against the plain branch in both arm orders.

4Legal source the compiler refuses

bug · LRM example refused · FIXEDA white-space-separated hex literal whose digits begin with a decimal digit followed by a, e or f is lexed as a real numberLRM 2.6.1 Example 5 p.15
Enhancement-515 implemented the three-token form of 2.6.1 (“It shall be legal to macro substitute these three tokens”, with white space allowed between base and digits) and the tracker names 'h 837FF as evidence. The LRM's Example 5 uses 32 'h 12ab_f001, and it does not compile:
32 'h 12ab_f001 error: unexpected token real number; expected integer 'h 1f error ('1f' = 1 femto) 'h 1e5 error ('1e5' = 100000.0) 'h 1a error ('1a' = 1 atto) 'h 837FF ok ('837' then 'FF': no scale letter follows a digit) 'h ab, 'h 3e ok 'h12ab_f001 ok (contiguous form)
Cause. After a bare base token the digit run is lexed as an ordinary number: lexer/src/lib.rs:437-446 turns a digit run followed by a Table 2-1 scale letter (a, f) or an exponent (e) into a Float, and parser/src/grammar/expressions.rs:259-266 (based_digit_tokens) joins only INT and IDENT tokens onto the base. The fix is a lexer mode for the token after a BASE_PREFIX, or accepting a Float token there and re-reading its text as hex digits.
Resolved (2026-09-03, after the audit), by both halves of that sentence. A bare base token now arms a lexer mode: the next non-trivia token, when it starts with a digit legal for the base, is lexed as a bare digit run (trivia keeps the mode armed; a define boundary or any non-digit disarms it). And the parser's digit join accepts number tokens of every kind, so digits substituted from a macro body — where they lex with no base before them, e.g. a body of 1f — join too; the value computation re-validates every digit against the base, so illegal-digit errors, the don't-care rule, and every previously working form are unchanged. Verified: the LRM's 32 'h 12ab_f001 = 313257985, the 'h 1f/'h 1e5/'h 1a/'h 1f2a family, base and digits each or both from macros, and spaced don't-care digits in a casex item; pinned by four new checks in examples/lrmlex_examples/ (30 checks, both solvers) and two lexer unit tests. The fast and slow cargo tiers (208 + 234) and the full 455-suite example sweep pass on the fixed compiler.
repro: hexlit.va (compiles clean after the fix)
missing · LRM example refused · FIXEDNull arguments to cross, above and timer are a type error, so the LRM's sample-and-hold does not compileLRM 5.10.3.1 / 5.10.3.2 / 5.10.3.3, Syntax 5-16 to 5-18
All three event functions are declared with analog_expression_or_null in every optional position, and 5.10.3.1's second example is @(cross(V(smpl) - thresh, dir, , , en === 1'b1)): tolerances left to the simulator, an enable supplied. The shipped compiler rejects every null form, with a diagnostic that names an internal type rather than the construct:
@(cross(V(p,n) - 0.5, dir, , , en)) error: type mismatch: expected real value but found _[0:0] value @(above(V(p,n), , 1e-3)) same @(timer(0, , 1e-9, 1)) same @(cross(V(p,n) - 0.5, dir, 0, 0, en)) ok (explicit zeros, which 5.10.3.1 also allows)
The clause offers explicit zeros as an alternative (“If a value of zero (0.0) is specified, the simulator shall apply a suitable value”), so a model can be rewritten; a model taken from the standard, or from a library written to it, cannot be compiled. It is the same feature that Enhancement-453 implemented for the analog operators, whose null argument round 2 verified for laplace_zp.
Cause. parser/src/grammar/call.rs:25-66 (E-453) represents a null argument as an empty ARRAY_EXPR, which is what the Laplace lowering expects. hir_ty/src/inference.rs:499-525 (infere_event_control) types every child expression of an event as Val(Type::Real), or Condition for the enable, and the empty array fails that requirement; the _[0:0] in the message is the empty array's type printed by the generic mismatch reporter. The event lowering then has no notion of “default” for a position, which explicit zeros already provide.
Resolved (2026-09-03, after the audit). The event arguments were already Option-shaped for trailing omission, so the fix is one filter at the AST-to-HIR boundary: a null argument in any optional position lowers to the same “not specified” an omission produces. Measured equivalences on a 1 kHz sine: a null dir counts both edges exactly as dir 0; null tolerances and enable count identically to the omitted and the explicit-zero spellings, and draw no not-honored warning; a null timer period is the one-shot form; a null enable is enabled. A null in the required first position is still refused, explicit tolerances keep their warnings and range checks, and the surplus-argument check is unchanged. The sample-and-hold compiles in the analog-subset spelling of its enable (V(en) > 0.5); the verbatim en === 1'b1 still stops on the separate mixed-signal boundary — reading a net's digital value — with an error naming the net reference. Pinned by four new checks in examples/lrmevents_examples/ (26 checks, both solvers); the fast and slow cargo tiers and the full 455-suite sweep pass on the fixed compiler.
repro: nullarg.va (compiles clean after the fix)
missing · LRM example refused · FIXEDNon-constant string replication, which 3.3's example marks OK, is refusedLRM 3.3 Table 3-3 p.26
Table 3-3 defines replication on strings with “multiplier must be of integral type and can be nonconstant”, and the clause's example annotates a = {i{"Hi"}}; // OK (non constant replication). The compiler requires a literal:

missing · FIXEDThe macro operators `", `\`" and `` are not implementedLRM 10.4 (by reference to IEEE 1364-2005 19.3.1)
10.4 defines `define by reference: “The 'define and 'undef compiler directives are described in IEEE Std 1364 Verilog”, and 1364-2005 19.3.1 specifies the three operators that let a macro build a string literal or paste tokens. All three are lexer errors:
`define STR(x) `"x`" error: encountered unexpected token! (at `") `define PASTE(a,b) a``b error at `` `define QUOTE(x) `"x is \`"x\`"`" error at `" `define MAX(a,b) ((a)>(b)?(a):(b)) ok (arguments, nesting, `ifdef/`elsif, `undef: all exact)
These are the mechanism by which a compact-model header generates $strobe messages and parameter names from one macro; a library that uses them stops at the first line. Missing rather than wrong: nothing is silently mis-expanded.
Resolved (2026-09-03, after the audit). The three operators lex as their own tokens inside a `define body (outside macro text every character keeps its old meaning), are stored as markers in the macro body, and are interpreted at expansion: a `" ... `" region becomes one string literal built after argument substitution, with spacing reconstructed from the define's own source and `\`" contributing an escaped quote; `` glues the adjacent post-substitution tokens and re-lexes them, valid only when they form exactly one token. The synthesized text — which exists in no source file — accumulates in a scratch buffer the preprocessor flushes into a virtual file at the end of the run, so the new tokens' spans resolve through the source map like any others (the same virtual-file device the `__FILE__ pre-pass and the -D definitions already use). Verified: the audit's three defines, 1364-2005's own `define home(filename) `"/home/mydir/filename`", a chained paste, pastes forming declarations, lvalues and numbers, multi-token stringify with spacing preserved byte-for-byte, and the empty string; unterminated regions, a paste with a missing operand, glue that does not re-lex to one token, and operators outside macro text are all located errors. Pinned by three new checks in examples/lrmlex_examples/ (33 checks, both solvers) and a lexer unit test; the fast and slow cargo tiers and the full 455-suite sweep pass on the fixed compiler.
repro: macroq.va (compiles clean after the fix)
