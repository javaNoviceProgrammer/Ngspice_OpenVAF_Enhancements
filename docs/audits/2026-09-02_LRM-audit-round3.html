Conformance audit · Accellera VAMS-2023 · third pass, twelve areas

The third LRM audit: nine divergences, and all of them are about output

An independent pass over openvaf-r and the ngspice-46 OSDI layer against the Verilog-AMS 2023 LRM. The August audit fixed 39 bugs; the September re-audit fixed five more and left the numerical core in good order. This pass went at the places the first two swept past — the timing and addressing of everything a model says to the outside world. Nine findings, every one reproduced against the shipped binaries and traced to a named line. Four lose data silently: an analog initial block's entire output is discarded, a file reopened for writing swallows every write, a negative multiplicity turns a resistor into a source, and the thirty-first output file writes into a descriptor that goes nowhere.

1The verdict

The arithmetic is not the problem and was not the problem last time either. What this pass found is that a model's voice — display, files, diagnostics — is routed by machinery that three separate clauses constrain, and the machinery covers some of them and not others.

Two prior audits established that the compact-model core is right: contributions, derivatives, filters, noise, parameter resolution. Round 2 then found that the failures had migrated to state that spans calls — a file position, an instance identity, a nature's tolerance. This round pushed one step further along the same line and found the next stratum: state that spans iterations. Every finding here is a question of when a message is emitted, or where it is addressed, and none is a mistake in a formula.

The sharpest result is a single-module experiment. Put six display tasks and one file write in an analog initial block. Run three analyses. $debug and $info print three times each — which proves the block executed in every analysis — and $strobe, $display, $write, $monitor and $fdisplay produce nothing at all, with the output file created and left at zero bytes. LRM 5.2.1 forbids access functions, analog operators, contributions and event controls inside that block, so initialising variables and reporting are the only two things it is allowed to do, and one of the two is silently discarded.

The second sharpest is a two-line diff. In one diode .op, from the same analog block: $strobe prints one line at the converged point; $warning prints twenty-one, walking the whole unconverged Newton sequence 0 → 1.000000 → 0.974135 → … → 0.629443. That is verbatim the headline of the August audit — "every display fired on every Newton iteration" — surviving on the one family of tasks the remediation did not sweep, and the clause that governs them (9.7.3) states the rule in its own words rather than by reference to 9.4.6, which is very likely why it was missed.

Reading the three groups together, one pattern explains five of the nine: a guard exists, is correct, and does not cover every route into the thing it guards. Display deferral covers $strobe but not $warning. The immediate-print tag covers @(initial_step) but not analog initial. ngspice's multiplicity check covers the netlist m= but not the Verilog-A #(.$mfactor(…)). The descriptor split introduced by E-539 reserves bit 31 for file descriptors, and the multichannel allocator still hands bit 31 out; the same enhancement's mode-change reopen covers write → read and not read → write. In each case the reasoning that produced the guard applies unchanged to the uncovered route.

2How this pass ran

Twelve areas, chosen by first reading the two prior audits' coverage maps and then deliberately not repeating them. Both earlier passes were organised by LRM chapter; this one was organised by mechanism, on the theory that a chapter-shaped sweep will systematically miss anything whose specification is split across chapters — which is exactly what LRM 9.4.6, 9.5.9 and 9.7.3 do to the accepted-iteration rule.

Two instruments were new here. The first was an exhaustive existence sweep of the system-function surface: 108 call sites — every entry in LRM Tables 9-1 through 9-18 marked “supported in analog context: Yes”, plus the entries marked No, so that both “missing” and “correctly refused” are measured facts rather than impressions — each compiled on its own. It produced no bugs: everything the tables require is present, the one absence is a disclosed subset boundary, and every refusal is one the tables ask for. Worth knowing in itself — the gaps are not in what exists.

The second was paired measurement. Rather than checking one task against the clause, each test puts the suspect task and a known-good sibling in the same block of the same module, so the comparison controls for the deck, the analysis, the instance and the iteration count. $strobe beside $warning; @(initial_step) beside analog initial; #(.$mfactor(3)) beside #(.$mfactor(-3)). Every headline number below is one of those pairs, which is why none of them needs an argument about what the simulator “should” have done.

Each finding was then pushed until it named a cause in openvaf/hir_lower, openvaf/hir, openvaf/osdi/stdlib.c or ngspice-46/src/osdi, and each was re-run against the committed binaries. Candidates that turned out to be documented, deliberate, or correct on a closer reading of the clause are in §7 rather than deleted — including one that reproduced perfectly and is not a finding.

3Output that is lost, doubled, or misrouted

bug · silent · FIXED (E-541)Every display task and every file write in an analog initial block is discardedLRM 5.2.1 / 9.4.6 / 9.5.9
LRM 5.2.1 gives the analog initial block one job — “simulation initialization purposes” — and then forbids, inside it, access functions, analog operators, contribution statements and event control statements. What remains is assigning variables and reporting. The reporting half produces no output whatsoever, in every analysis, and the file it opens is created and left empty, so nothing looks wrong.
One module, one analog initial block holding the six display tasks and one open–write–close file sequence, three analyses (op, tran, dc):
$debug 3 lines (once per analysis) <- proves the block ran $info 3 lines (once per analysis) $strobe 0 lines $display 0 lines $write 0 lines $monitor 0 lines $fdisplay 0 bytes (INIT.txt created, size 0)
The paired control is decisive: move the identical statements into @(initial_step) in the same module and all of them appear. Same tasks, same instance, same analysis — only the enclosing construct differs.
analog initial begin $strobe("INIT-strobe"); $display("INIT-display"); $info("INIT-info"); end @(initial_step) begin $strobe("EVT-strobe"); $display("EVT-display"); $info("EVT-info"); end observed: OSDI(info) n1: INIT-info <- only the immediate-path task OSDI n1: EVT-strobe OSDI n1: EVT-display OSDI(info) n1: EVT-info
Cause. hir_lower/src/lib.rs:619 lowers the block into the eval function under make_cond(ParamKind::IsInitialStep, …) — correct for E-456's purpose, which was to stop the block re-running on every evaluation. But it does not set ctx.in_event_ctx, which hir_lower/src/stmt.rs:215 sets only while lowering an event-controlled statement, and which is what tags a display with LOG_FLAG_IMMEDIATE. Untagged, the output reaches osdi_log (ngspice-46/src/osdi/osdicallbacks.c:239) during the instance's first Newton iteration, is deferred into the pending buffer, and is then dropped by the next osdi_display_iter_begin as a superseded iteration. The file half takes the same route through osdi_io_iter_begin.
The comment sitting directly above that assignment states the hazard exactly, for the neighbouring construct: “the event fires on its own Newton iteration, so deferring their output to the accepted iteration (LRM 9.4.6) would drop it entirely”. analog initial fires on the initial-step iteration for precisely the same reason and did not get the tag. This is the third appearance of one hazard — E-516 handled it for event-gated statements, E-535 (hunt N5) for re-entered setup code, and the analog initial route is still open.
repro: cbig.va / cbig.cir · paired control: ini.va, fw.va
bug · FIXED (E-541)$error, $warning and $info execute on every Newton iteration, including rejected onesLRM 9.7.3 p.237
LRM 9.7.3 is explicit and self-contained: “Non-fatal system severity tasks ($error, $warning, $info) called during a rejected iteration shall have no effect. $fatal terminates the simulation without checking whether the iteration would be rejected.” The rule is stated for this family in its own words, not by reference to 9.4.6 — and the split it draws is exactly one task wide.
One diode .op. $strobe and $warning sit on adjacent lines of the same analog block:
$strobe -> 1 line OSDI n1: S v=0.629443 <- the converged point $warning -> 21 lines OSDI(warn) n1: W v=0.000000 OSDI(warn) n1: W v=1.000000 OSDI(warn) n1: W v=0.974135 ... 16 more unconverged iterates ... OSDI(warn) n1: W v=0.629443
Over a 5-point DC sweep the same pairing gives 5 lines from $strobe and 12 from each severity task: one at v=0 before the sweep begins — output displayed when no iteration has been accepted at all, which is the negative half of 9.4.6 as well — then one per Newton iteration at each of the five points (three at the first, two at each of the rest).
Cause. ngspice-46/src/osdi/osdicallbacks.c:239. The deferral gate tests the level:
if (display_managed && (level == LOG_LVL_DISPLAY || level == LOG_LVL_MONITOR) && !(lvl & LOG_FLAG_IMMEDIATE)) { ... defer ... }
LOG_LVL_INFO, LOG_LVL_WARN and LOG_LVL_ERR fall through to the immediate switch. LOG_LVL_FATAL falling through is correct — the clause says so — so the fix is bounded to adding the three non-fatal levels, and $debug and $fatal must stay out.
Prior art, and it is partial. Enhancement-516 contains the sentence “the compiler knows the gating: statements lowered inside an event control carry a new LOG_FLAG_IMMEDIATE bit (and $fdebug/severity tasks keep their immediate paths)” — a parenthesis inside a paragraph about event gating, with no clause cited. Thirty-four lines earlier the same document states the exemption as “only $fdebug exempt”. So the behaviour was chosen, but chosen by grouping the severity tasks with $debug, which is the one task 9.4.6 exempts and the one task 9.7.3 does not cover. The compliance tracker records only that $warning/$error/$info “display”; no document weighs 9.7.3 against the choice. It is reported here as a divergence, with the prior decision quoted rather than paraphrased.
repro: dio.va / dio.cir (21 vs 1) · pair.va / pair.cir (12 vs 5)
bug · FIXED (E-541)$error in an analog initial block lets the simulation proceed past initializationLRM 9.7.3 p.237
The clause is unambiguous: “If $error is executed within an analog initial block, then the message is issued and the initialization continues. However, the simulation shall not proceed past initialization.” This is the standard's designated way for a model to reject a parameter combination it cannot serve. Observed: the message prints, the operating point runs to completion, and the deck gets numbers.
OSDI(err) n1: ERR from analog initial v(1) = 1.000000e+00 <- LRM: this solution must not be produced REACHED-END
The mechanism to stop after initialization exists and is demonstrably wired up — the same model with $fatal in place of $error aborts exactly as it should, producing “a Verilog-A device raised $fatal during the operating point; aborting” and no v(1). Only $error does not reach it.
Cause. hir_lower/src/expr.rs:2591 lowers $fatal as a display plus CallBackKind::SetRetFlag(RetFlag::Abort), which osdiload.c:1035 turns into E_PANIC. BuiltIn::error (same file, line 2402) emits the display and nothing else, and no RetFlag expresses 9.7.3's weaker “finish after initialization, do not start the analysis”.
The same clause's reporting requirement is also unmet, for all four tasks: “these tasks shall also report the simulation run time at which the severity system task is called. If any of these tasks is called from an analog context during a dc sweep, the simulator shall report the current value of the swept variable in place of the simulation run time. If the task is called from an analog initial block, the simulator shall report that the call was made during initialization.” Messages carry the instance name and nothing else, in every analysis — which is the same complaint 9.4.4 makes about %m, on a family where the LRM spells the requirement out.
measured in a dc sweep: OSDI(warn) n1: v is high (0.75) <- no swept value measured in a transient: OSDI(warn) n1: v is high (0.5312) <- no time repro: sev.va + si3.cir · control: fat.va + fatbody.cir · context: sev2.va
bug · silent · FIXED (E-541)The thirty-first multichannel descriptor is 0x8000_0000, the bit the LRM reserves — and writes to it vanishLRM 9.5.1 p.229
LRM 9.5.1: “The most significant bit (bit 31) of a multichannel descriptor is reserved and shall always be cleared, limiting an implementation to at most 31 files opened for output via multichannel descriptors.” Bit 0 is stdout, so the usable range is bits 1–30 and the ceiling is 30 user files. The allocator runs to bit 31.
$fopen("e0.txt") -> 2 (bit 1) ok ... $fopen("e29.txt") -> 1073741824 (bit 30) ok, and this is the last legal one $fopen("e30.txt") -> -2147483648 (bit 31) LRM: shall always be cleared $fopen("e31.txt") -> 0 correct failure indication
The consequence is not cosmetic, and it is specific to this tree. Enhancement-539 implemented the clause's two-namespace split by taking bit 31 as the file-descriptor marker (OSDI_FD_BIT 0x80000000u), with 0x8000_0000 itself being STDIN. So the thirty-first multichannel descriptor is bit-identical to the pre-opened read-only standard input, and the runtime resolves it that way: a $fdisplay to it is silently discarded — it does not reach the file, and it does not reach stdout either.
$fdisplay(<31st mcd>, "THIS-SHOULD-GO-TO-ex2/e30.txt") ex2/e30.txt : 0 bytes stdout : nothing
Cause. openvaf/osdi/stdlib.c:754 — the free-slot scan is for (int b = 1; b < OSDI_MCD_BITS; b++) with OSDI_MCD_BITS defined as 32 (line 609), so bit 31 is allocatable. The dedup scan (line 742) and both close loops (974, 1016) share the bound. The clause's own arithmetic — bit 0 reserved below, bit 31 reserved above, 31 files — is the check that was not applied.
repro: exh.va / exh.cir (allocation), exh2.va / exh2.cir (the lost write)
bug · silent · FIXED (E-541)Reopening a file in a different mode is ignored, and every write to it is silently lostLRM 9.5.1 Table 9-24 p.229
Table 9-24 gives "w" as “truncate to zero length or create for writing” and "a" as “append; open for writing at end of file”. Read a file, close it, reopen it for writing, and the descriptor handed back is the read-mode stream — so the file is neither truncated nor appended to, and the writes disappear without an error.
The paired control is in the same block of the same module. One file is opened "a" with no prior open; the other is read first:
control $fopen("mode2.txt","a") -> AAAA / BBBB / CCCC-control appended, correct finding $fopen("mode3.txt","r"); $fgets(...) $fclose(...) $fopen("mode3.txt","w") -> same descriptor as the read open $fdisplay(..., "DDDD-should-be-only-line") mode3.txt afterwards: AAAA / BBBB file untouched, write lost
The read-then-rewrite shape is not exotic — a model that loads a calibration table at initialization and writes an updated one back is exactly it — and nothing on any channel says the write did not happen.
Cause. openvaf/osdi/stdlib.c:774, the same-name dedup in osdi_fopen. Two branches can honour a reopen: a rewind, gated on readable && osdi_file_readable[i], and a real freopen, gated on !osdi_io_managed — which never holds under the simulator. Anything else falls through to osdi_file_close_req[i] = 0; return enc;, returning the existing stream in its original mode. The comment on the rewind branch names the general rule precisely — “reopening a write-mode stream for reading is a MODE CHANGE and needs the freopen below” — and E-539 implemented it for that direction, after a first attempt in the other direction broke stringio_examples. The read → write direction is the half still open, and it fails silently where the broken write → read case at least produced visibly wrong data.
repro: mch2.va / mch2.cir (control + finding) · mch.va (the append variant)

4Values the LRM bounds and nothing checks

bug · silent · FIXED (E-541)A negative $mfactor set from Verilog-A sign-inverts the device, with no diagnostic on any channelLRM 9.18 Table 9-29 p.249
Table 9-29's Allowed values column reads $mfactor > 0. A multiplicity is a count of identical devices in parallel; a negative one is not a small device, it is a reversed one.
leaf: I(p,n) <+ V(p,n)*1e-3 (a plain 1 kΩ resistor) leaf #(.$mfactor( 3)) -> i(v1) = -3.00000e-03 correct: sinks 3 mA leaf #(.$mfactor(-3)) -> i(v1) = +3.000000e-03 the resistor now SOURCES 3 mA leaf #(.$mfactor( 0)) -> i(v1) = 0.000000e+00 the device silently disappears
What makes this a finding rather than a missing nicety is that the same illegal value is caught, precisely, on the netlist route. Write m=-3 on the instance line and ngspice says so and ignores it:
Warning: n2: multiplier m=-3 is negative; the device's contribution is sign-inverted (a passive device becomes active) and any noise contribution becomes NaN. Warning: multiplier m=-3 is negative; the value is ignored. -> i(v2) = -1.00000e-03 (m clamped to 1)
So the hazard is understood, the consequence is written down in the message, and the check simply does not cover the Verilog-A route. There is a second partial guard, too: give the leaf a white_noise contribution and the compiler rejects the same model at compile time — because the noise scaling divides by sqrt($mfactor) and the constant-folded sqrt(-3) trips the domain check. A model without noise gets no such luck.
error: sqrt: the argument is -3, which is outside the domain of sqrt (values >= 0); the result would be NaN
Cause. Three composition sites share one shape and none validates: hir/src/elaborate.rs:2925 (merge_sys_overrides, composing inherited overrides), hir/src/elaborate.rs:3065 (rewriting each $mfactor-family read in an inlined body), and hir_lower/src/state.rs:107 (the MIR composition for paramset and netlist overrides). Each picks * or + from ParamSysFun::composes_multiplicatively and emits it. Enhancement-44 documents the two composition rules and records the six defaults; the Allowed values column of the same table is not mentioned there or anywhere else in the tree.
repro: mfva.va / mfva.cir
bug · FIXED (E-541)$angle is never reduced modulo 360, and the other three bounds are unchecked on both routesLRM 9.18 Table 9-29 p.249
Table 9-29 gives $angle the resolution rule “$anglespecified + $anglehier, modulo 360 degrees” and the allowed range “0 ≤ $angle < 360”. The sum is implemented; the modulo is not. Two levels of hierarchy, 200° at each:
top -> mida #(.$angle(200)) -> leafb #(.$angle(200)) observed: angle=400 LRM: angle=40 (the same deck confirms the other rules ARE right: hflip = (-1)*(-1) = +1 multiplicative, correct xposition = 0.002+0.001 = 0.003 additive, correct)
Separately, every Allowed values entry is unenforced, and on both ways of setting these parameters — the Verilog-A #(.$angle(…)) form and ngspice's _angle= instance form:
Verilog-A: leafb #(.$angle(400), .$hflip(2), .$vflip(0), .$mfactor(-3)) -> angle=400 hflip=2 vflip=0 m=-3 netlist: n1 1 0 mm _angle=400 _hflip=5 _vflip=0 -> angle=400 hflip=5 vflip=0 LRM 9-29: 0 ≤ angle < 360 ; hflip, vflip ∈ {+1, −1} ; mfactor > 0
A model that uses the angle trigonometrically is unharmed — 400° and 40° have the same sine — which is why this can sit unnoticed. A model that compares it is not: if ($angle < 90), a quadrant lookup, or a table keyed on orientation all take the wrong branch, and the LRM's range is exactly the contract such a model is entitled to rely on. Same three lines as the finding above.
repro: ang.va / ang.cir (modulo) · rng1.va, hsp.va (ranges, both routes)

5Lower severity

missing diagnostic · FIXED (E-541)Two errors LRM 9.20 mandates for the node-alias functions are not raisedLRM 9.20 p.253
The clause states three “shall be an error” rules for $analog_node_alias/$analog_port_alias. The context rule — a call outside an analog initial block — is enforced, with a good message. The other two are not:
$analog_node_alias(p, "top.x") p is a PORT LRM: "It shall be an error for the analog_net_reference to be a port or to be involved in port connections." -> compiles clean $analog_node_alias(loc2, "top.loc1") loc1 is another call's net reference LRM: "It shall be an error for the hierarchical_reference_string to reference a node that is used as an analog_net_reference in another ... call." -> compiles clean
Severity is low because both functions are a documented always-return-0 stub (compliance §7.5 — the clause's own unresolvable-reference value), so nothing numerically wrong follows. It is recorded because the tracker's wording, “their 9.20 context rule is enforced”, is true of the one rule it names and reads as covering the clause.
repro: al.va
deviation · FIXED (E-541)$write cannot compose a line: every call carries its own instance prefixLRM 9.4.1 p.226
LRM 9.4.1: “The $write task provides the same capabilities as $strobe, but with no newline.” Suppressing the newline has one purpose — assembling a line from several calls — and the per-message OSDI <instance>: prefix (E-377, and genuinely useful on every other task) is emitted per call, so the pieces cannot join:
$write("[A]"); $write("[B]"); $write("[C]\n"); observed: OSDI n1: [A]OSDI n1: [B]OSDI n1: [C] wanted: OSDI n1: [A][B][C]
A prefix emitted on the first fragment after a newline, rather than on every call, would keep the diagnostic value and restore the construct. Recorded as a deviation rather than a bug: no data is wrong, and the prefix is a deliberate local improvement. Two conformant neighbours were checked in the same deck — a bare $strobe; prints exactly a newline (9.4.1), and $debug prints on every iteration (9.4.6's sole exemption).
repro: wr.va / wr.cir

6What was measured and holds

Positive results, each an independent expectation checked against the shipped binaries. Several are the direct neighbours of findings above, which is what makes the findings interpretable.

analog initial semantics (LRM 5.2.1) — every rule but the output

All four statement restrictions are enforced, each with a diagnostic that names the construct rather than the parse:

access function -> error: nature access is not allowed in analog initial block analog operator -> error: analog operator 'ddt' is not allowed in analog initial block contribution -> error: branch contributions are not allowed in analog initial block event control -> error: event control statements are not allowed in analog initial block

And the re-execution rule holds — “If a parameter or variable that is referenced from an analog initial block is changed during a sub-task of a parameter sweep analysis, then the analog initial block shall be re-executed”. Sweeping an instance parameter the block reads tracks it exactly across all five points (g0 = 1…5 mS → i = −1…−5 mA), rather than freezing at the first.

File I/O — the deferral, the modes, and the failure values

  • LRM 9.5.9 holds for file writes. The identical diode .op that produces 21 $warning lines produces exactly one $fstrobe line, at the converged v=0.629443. The file machinery does what the severity machinery does not.
  • All fifteen Table 9-24 modes open — r rb w wb a ab r+ r+b rb+ w+ w+b wb+ a+ a+b ab+ — and every file descriptor carries bit 31 as 9.5.1 requires (the first user descriptor is 0x8000_0003, immediately above the three pre-opened streams).
  • Failure returns zero, per 9.5.1: a missing file opened "r" gives 0, and so does an unrecognised mode string.
  • Multichannel channels are reused after close, per 9.5.1, on the instance-setup path: open/close/open returns the same channel rather than consuming a new one.

The system-function surface (Tables 9-1 – 9-18)

All 108 call sites were compiled individually — every Table 9-1 – 9-18 entry marked supported in the analog context, plus the entries marked unsupported, so that a refusal is measured rather than assumed. Everything the tables mark supported is present and compiles, except $bitstoreal/$realtobits, which are a disclosed subset boundary (their 64-bit vector operand type has no analog counterpart). The four rejections are all correct: $monitoron/$monitoroff (Table 9-1, analog: No), $time (Table 9-7, analog: No), and $receiver_count (connectmodule-only, outside Annex C). $simprobe and $limit reject with the LRM's own fallback wording plus a located warning.

$simparam (LRM 9.15, Table 9-27)

Nine of the thirteen table names are served with sensible values — gdev 1e-12, gmin 1e-12, iteration, scale 1, simulatorVersion 46, simulatorSubversion 0, sourceScaleFactor 1, tnom 27; the clause's “if they support the parameter” makes the other four legitimately absent. The normative half is the error behaviour, and it is exact: an unknown name with a default returns the default silently, and an unknown name without one is a located compile warning and a run-time fatal — “an error is generated”, as 9.15 requires. The warning even enumerates the served names.

Display formatting (Tables 9-21 – 9-23)

Every conversion works in both cases, which the tables specify as alternatives (“%h or %H”) and no repository document had claimed: h/H o/O b/B d/D c/C s/S e/E f/F g/G r/R m/M. %H yields upper-case hex and %E an upper-case exponent, matching C. %m names the instance (E-539) in both spellings.

$table_model tie-breaking (LRM 9.21.4)

The clause has one rule that a plausible implementation gets wrong: “When the lookup ordinate is equidistant from two bracketing samples the function snaps away from zero.” On samples at −4, −2, +2, +4 with closest-point lookup "D", a lookup at +3 returns the +4 sample and a lookup at −3 returns the −4 sample. Both correct.

7Things that looked wrong and are not

Recorded so a fourth pass does not spend its budget here. Each reproduced exactly as described; none is a finding.

documented, not newA constant-argument display prints twice at setup and never at an accepted point
A $strobe whose arguments do not depend on the operating point is hoisted into instance initialization, so it prints twice (setup and temperature update) and then not at all: in a 5-point DC sweep it yields 2 lines where an op-dependent $strobe beside it yields 5. This was the first thing this pass found and it is fully on record — E-516's “Remaining, documented” section names it, and the compliance tracker §7.1 carries it as “a constant-argument display hoisted to instance initialization still executes there (⚠️ documented at the split)”. Reported here only as evidence that the prior-art check was run before the write-up, not after.
deliberateWriting to a descriptor after $fclose still reaches the file, and the channel is not reused
LRM 9.5.1 says “No further output to or input from any file descriptor(s) closed by $fclose is allowed” and “$fopen shall reuse channels that have been closed”. Under the managed path neither is observable, because 9.5.9 requires the close itself to be deferred to the accepted iteration: within one evaluation the stream is still open, so a stray write lands and a reopen takes a fresh channel. That deferral is E-516's design and it is the right reading of the two clauses together — a close executed on a superseded iteration would destroy accepted output. On the unmanaged instance-setup path, where no such conflict exists, reuse works correctly (open/close/open returns the same channel). Recorded as a deviation forced by a clause conflict, not a defect.
permissive extension$fgetc, $ungetc and $realtime are accepted although Table 9-2/9-7 mark them analog: No
